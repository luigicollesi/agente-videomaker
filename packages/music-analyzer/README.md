# Music Analyzer — implementation milestone 1

CPU-first decoder foundation for the Music Analyzer system skill.

## Setup

Requires Python 3.12+, FFmpeg and FFprobe on PATH.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -e '.[test]'
pytest -q
music-analyzer inspect /path/to/music.mp3
music-analyzer decode /path/to/music.mp3 --pcm-output /tmp/music.f32le --metadata-output /tmp/music-decoded.json
```

The CLI currently implements only stream inspection and PCM decoding.
It does **not** yet produce `music-analysis.json` or expose `analyze_music`,
`get_music_context`, or `validate_music_analysis`.

## Temporal integrity

The metadata marks `timestamp_mapping=unverified` and
`timeline_offset_seconds=null` until alignment with the desktop editor
is established. Do not interpret decoded PCM timestamps as verified
source-timeline event positions.

Next milestones: timebase verification, schema v1, DSP, segmentation,
expressive heuristics and desktop tool registration.

## DSP milestone (experimental)

The analyzer now supports a preliminary `analyze` command:

```bash
music-analyzer analyze /path/to/audio.wav --output /tmp/music-analysis.json
```

Output includes estimated BPM/beats, onset events, RMS dBFS, spectral
centroid, rolloff and flatness curves every 0.5s. The source timeline mapping
is still **unverified**. Downbeats, segmentation, chroma, expressive heuristics,
strict schema validation, caching, and editor integration are not available yet.

Do not mistake estimated BPM or acoustic attack strength for calibrated confidence.


## Temporal context milestone V0.3 (experimental)

The `analyze` command now includes conservative change-point segmentation,
three-second energy-rise/drop event candidates, and acoustic descriptors
based on RMS, spectral centroid and flatness. These are heuristic acoustic
characterizations, **not** detected chorus/verse sections or emotions.

```bash
music-analyzer analyze /path/to/song.wav --output /tmp/music-analysis.json
music-analyzer context /tmp/music-analysis.json --start 80 --end 105
```

The `context` command returns bounded beat and change event arrays,
an onset count, average RMS and overlapping segments. Its timebase remains
relative to decoded PCM, not verified editor timeline. Existing JSON files
generated by V0.2 must be regenerated to include segments and new events.

## Objective features milestone (experimental)

The latest analyzer emits measured/estimated data only:
- `rhythm.advanced.local_bpm_curve` — beat-interval-based BPM hypotheses in 8-second windows
- `rhythm.advanced.onset_density_curve` — attacks per second over each local window
- `rhythm.advanced.beat_interval_cv` — global timing variability
- `dynamics` — RMS dBFS quantiles and summary (not LUFS)
- `segments[].evidence` — quantitative segment medians, with no style/emotion labels
- CLI `onset_count` now excludes change-point and energy events

Re-run `music-analyzer analyze` to regenerate the JSON. Existing historical
analyses are not automatically migrated. This milestone does not implement
LUFS, pitch, full spectral descriptors, source-time alignment, style/emotion
classification, or editor registration. Validation with real audio is pending.

## Additional objective measurements (experimental)

The current analysis includes per-0.5s `spectral_bandwidth_hz`,
`zero_crossing_rate`, `spectral_contrast_mean_db` and a 12-element
`chroma_energy` vector, plus global `signal_diagnostics`:
sample peak, global RMS, crest factor, DC offset, near-full-scale fraction.
These are DSP measurements, not inferred chords, emotions or instruments.

For 332-second input, chroma/contrast extraction can increase CPU and memory
use. The current implementation still materializes a full STFT matrix;
bounded chunked STFT and verified editor timing remain future requirements.
Tests include synthetic tones and silence; successful local validation with
the complete user track and CI run must still be confirmed.

## EBU R128 loudness measurements

The analyzer now records `loudness.integrated_lufs`,
`loudness.loudness_range_lu`, and `loudness.true_peak_dbtp`
using FFmpeg loudnorm's input measurement pass. No normalization is
applied to the signal used for DSP.

Reference execution on Inferno-Divina_Comedia.wav (332 s) measured
-14.62 LUFS integrated, 7.40 LU LRA, and -2.68 dBTP true peak.
This is a direct FFmpeg measurement on the attached source, not a
passing end-to-end test of the Python analyzer.

Spectral processing is **still full-matrix and not memory-bounded**.
Do not claim chunked STFT support. Genre, emotion, key and chord
classification remain outside the implemented scope.

## Chunked spectral processing and stereo diagnostics (experimental)

`dsp.measure_pcm` now uses overlapping spectral frame batches of 512 frames,
rather than allocating one full-song STFT magnitude matrix. Frame centers
remain aligned to the decoded PCM hop grid. Chroma tuning is fixed at zero
for cross-batch comparability. The onset envelope now uses positive normalized
spectral flux; onset and BPM counts **may differ** from older analyses.

`stereo` reports channel RMS, channel correlation and Mid/Side energy ratio
when the source has exactly two channels. `signal_diagnostics.sample_peak_dbfs`
is measured on the decoded/resampled mono signal; values above 0 dBFS are
possible after processing and do not prove clipping in the original source.
Use `loudness.true_peak_dbtp` to evaluate the original-stream peak estimate.

The onset envelope is still computed on the full frame-rate flux vector, and
beats are tracked globally. Spectral matrices are bounded by the batch size,
but the entire analysis is **not** constant-memory in audio duration.
CI and full-track numerical regression must pass before this is considered stable.
