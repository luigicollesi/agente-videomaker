# Music Analyzer — implementation milestone 1

CPU-first decoder foundation for the Music Analyzer system skill.

## Setup

Requires Python 3.12+, FFmpeg and FFprobe on PATH.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -e '.[test]'
pytest -q
music-analyzer inspect /path/to/music.mp3
music-analyzer decode /path/to/music.mp3 --pcm-output /tmp/music.f32le --metadata-output /tmp/music-decoded.json
```

The CLI currently implements only stream inspection and PCM decoding.
It does **not** yet produce `music-analysis.json` or expose `analyze_music`,
`get_music_context`, or `validate_music_analysis`.

## Temporal integrity

The metadata marks `timestamp_mapping=unverified` and
`timeline_offset_seconds=null` until alignment with the desktop editor
is established. Do not interpret decoded PCM timestamps as verified
source-timeline event positions.

Next milestones: timebase verification, schema v1, DSP, segmentation,
expressive heuristics and desktop tool registration.

## DSP milestone (experimental)

The analyzer now supports a preliminary `analyze` command:

```bash
music-analyzer analyze /path/to/audio.wav --output /tmp/music-analysis.json
```

Output includes estimated BPM/beats, onset events, RMS dBFS, spectral
centroid, rolloff and flatness curves every 0.5s. The source timeline mapping
is still **unverified**. Downbeats, segmentation, chroma, expressive heuristics,
strict schema validation, caching, and editor integration are not available yet.

Do not mistake estimated BPM or acoustic attack strength for calibrated confidence.


## Temporal context milestone V0.3 (experimental)

The `analyze` command now includes conservative change-point segmentation,
three-second energy-rise/drop event candidates, and acoustic descriptors
based on RMS, spectral centroid and flatness. These are heuristic acoustic
characterizations, **not** detected chorus/verse sections or emotions.

```bash
music-analyzer analyze /path/to/song.wav --output /tmp/music-analysis.json
music-analyzer context /tmp/music-analysis.json --start 80 --end 105
```

The `context` command returns bounded beat and change event arrays,
an onset count, average RMS and overlapping segments. Its timebase remains
relative to decoded PCM, not verified editor timeline. Existing JSON files
generated by V0.2 must be regenerated to include segments and new events.

## Objective features milestone (experimental)

The latest analyzer emits measured/estimated data only:
- `rhythm.advanced.local_bpm_curve` — beat-interval-based BPM hypotheses in 8-second windows
- `rhythm.advanced.onset_density_curve` — attacks per second over each local window
- `rhythm.advanced.beat_interval_cv` — global timing variability
- `dynamics` — RMS dBFS quantiles and summary (not LUFS)
- `segments[].evidence` — quantitative segment medians, with no style/emotion labels
- CLI `onset_count` now excludes change-point and energy events

Re-run `music-analyzer analyze` to regenerate the JSON. Existing historical
analyses are not automatically migrated. This milestone does not implement
LUFS, pitch, full spectral descriptors, source-time alignment, style/emotion
classification, or editor registration. Validation with real audio is pending.

## Additional objective measurements (experimental)

The current analysis includes per-0.5s `spectral_bandwidth_hz`,
`zero_crossing_rate`, `spectral_contrast_mean_db` and a 12-element
`chroma_energy` vector, plus global `signal_diagnostics`:
sample peak, global RMS, crest factor, DC offset, near-full-scale fraction.
These are DSP measurements, not inferred chords, emotions or instruments.

For 332-second input, chroma/contrast extraction can increase CPU and memory
use. The current implementation still materializes a full STFT matrix;
bounded chunked STFT and verified editor timing remain future requirements.
Tests include synthetic tones and silence; successful local validation with
the complete user track and CI run must still be confirmed.

## EBU R128 loudness measurements

The analyzer now records `loudness.integrated_lufs`,
`loudness.loudness_range_lu`, and `loudness.true_peak_dbtp`
using FFmpeg loudnorm's input measurement pass. No normalization is
applied to the signal used for DSP.

Reference execution on Inferno-Divina_Comedia.wav (332 s) measured
-14.62 LUFS integrated, 7.40 LU LRA, and -2.68 dBTP true peak.
This is a direct FFmpeg measurement on the attached source, not a
passing end-to-end test of the Python analyzer.

Spectral processing is **still full-matrix and not memory-bounded**.
Do not claim chunked STFT support. Genre, emotion, key and chord
classification remain outside the implemented scope.

## Chunked spectral processing and stereo diagnostics (experimental)

`dsp.measure_pcm` now uses overlapping spectral frame batches of 512 frames,
rather than allocating one full-song STFT magnitude matrix. Frame centers
remain aligned to the decoded PCM hop grid. Chroma tuning is fixed at zero
for cross-batch comparability. The onset envelope now uses positive normalized
spectral flux; onset and BPM counts **may differ** from older analyses.

`stereo` reports channel RMS, channel correlation and Mid/Side energy ratio
when the source has exactly two channels. `signal_diagnostics.sample_peak_dbfs`
is measured on the decoded/resampled mono signal; values above 0 dBFS are
possible after processing and do not prove clipping in the original source.
Use `loudness.true_peak_dbtp` to evaluate the original-stream peak estimate.

The onset envelope is still computed on the full frame-rate flux vector, and
beats are tracked globally. Spectral matrices are bounded by the batch size,
but the entire analysis is **not** constant-memory in audio duration.
CI and full-track numerical regression must pass before this is considered stable.

## JSON integrity validation

```bash
music-analyzer analyze /path/to/song.wav --output /tmp/music-analysis.json
music-analyzer validate /tmp/music-analysis.json
```

Validation checks chronological ordering, source duration bounds, overlapping
segments and non-finite numeric values. It does **not** establish musical
accuracy or source/editor-time synchronization.

## Rhythm regression fix

The initial bounded-spectral implementation replaced the proven
librosa Mel onset envelope with normalized positive spectral flux, causing
large deviations on the 332-second Inferno fixture (89.103 BPM / 1195 onsets
previously versus 123.047 BPM / 625 onsets afterward). The beat tracker now
uses the original `librosa.onset.onset_strength(y=..., sr=..., hop_length=512)`
method again. `normalized_spectral_flux` is still available in each sampled
spectral point and is **not** passed to the beat tracker.

`test_rhythm_regression.py` compares onset timestamps against the
independent librosa reference call on a controlled click signal. The revised
full-song results must still be checked with the user's local file; this
fix does not certify beat-grid accuracy against annotated ground truth.
The Mel onset computation continues to consume memory; spectral descriptor
STFT batches remain bounded separately.

## Incremental integration milestone: temporal dynamics and cache

Analysis now includes `temporal_dynamics.curve` (3-second robust RMS profile,
change relative to the preceding 3-second window) and acoustic trend events.
These are **RMS dBFS**, not LUFS or musical drops. The interval `context`
operation includes the same features.

To avoid repeating expensive calculations on unchanged audio, enable the
optional content-addressed cache:

```bash
music-analyzer analyze song.wav --output analysis.json --cache-dir ~/.cache/agente-music-analyzer
```

The cache keys include the SHA-256 of the source bytes, selected stream,
analyzer version and pipeline revision. Do not share the cache between
untrusted users; a cached JSON must not be treated as independently
authenticated ground truth. The default remains **no cache**.

This is an incremental milestone, **not** a completed V1.0 release. Verified
source/editor time mapping, full loudness-over-time measurement, harmonic CQT,
spatial time series, structural tempo warping, native editor registration, and
real-audio benchmarks remain outstanding.

## Agent CLI evidence tools (incremental milestone)

```bash
music-analyzer overview analysis.json
music-analyzer context analysis.json --start 90 --end 108
music-analyzer compare analysis.json --start-a 90 --end-a 108 --start-b 178 --end-b 196
music-analyzer cues analysis.json --start 90 --end 108 --limit 30
```

`compare` uses aggregate CENS and MFCC cosine similarity; the two metrics
are explicitly **not** calibrated probabilities, and interval aggregation
does not establish sequential matching. `cues` returns measured acoustic
events and RMS trend candidates, not mandatory cuts or named formal sections.
`overview` returns a compact global report without the full per-frame data.

The standard rhythm tracker is unchanged. `rhythm.alternatives` includes
half/standard/double tempo grid interpretations and 8-second median beat
interval estimates. These are *derived from the existing beat grid*, not
independent tempo trackers.

These changes do **not** constitute a completed V1.0 release: local EBU
loudness, verified source/editor mapping, CQT/Tonnetz, spectral HPSS,
stereo-local curves, tempo-warped structural matching, native editor tool
registration, and full real-audio benchmark validation remain to be done.

## Acoustic cues V2 and sequence comparison

```bash
music-analyzer cues analysis.json --start 90 --end 108 --limit 30 \
  --categories beat strong_onset energy harmonic_change structure_boundary \
  --selection representative

music-analyzer compare analysis.json \
  --start-a 90 --end-a 108 --start-b 178 --end-b 196
```

The V2 cues include existing detected beats and onsets. Onsets without
stored peak amplitudes are labeled `onset_unranked`: do not interpret them as
strong onsets. The `representative` selector spreads results across the
requested interval. The comparison now includes bounded constrained
multifeature DTW, in addition to legacy aggregate cosine comparisons.

The full analysis stores `structure_v3` **separately** from the validated
V2 structural candidate output. V3 uses multi-angle recurrence path
enhancement and is explicitly **experimental** until evaluated against
annotated music. The `quality` object reports these limitations.

`timebase.map_decoded_to_editor` only returns mapped editor seconds after
explicit verification; metadata alone cannot establish MP3/MP4/editor
alignment.

**Release gate:** This milestone is not a certified stable V1.0. Test it on
real media, compare with annotated boundaries, run a complete regression
suite, and confirm editor tool registration before releasing.

## Minimal stabilization: default V2, experimental V3 opt-in

```bash
music-analyzer analyze song.wav --output analysis.json
music-analyzer analyze song.wav --output experiment.json --experimental-structure-v3
```

The default standard analysis preserves Structure V2 and writes a
`structure_v3` object with `status: not_requested`. Use the experimental
flag only for benchmarking. The cache key includes this flag and the pipeline
revision, so V3 and default results cannot be confused.

The cue reader uses the preexisting `events[].strength` (whole-track
Mel-onset-envelope relative strength), rather than seeking an absent
`relative_strength`. Onsets without measured strength remain unranked.
A positive `--min-relative-strength` filter excludes unmeasured events.
Representative selection reserves one slot for each present cue category
where the result limit permits. These are interface improvements and do
not modify the number or positions of measured onsets or beats.

The DTW comparison preserves `normalized_alignment_cost` and adds
`mean_alignment_cost`, `path_length_ratio`, and `feature_coverage`.
No output is a calibrated musical similarity probability.
